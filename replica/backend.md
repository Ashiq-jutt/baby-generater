# Backend

Supabase (Postgres + Auth + Storage + Edge Functions), fal.ai for models,
RevenueCat over Apple/Google IAP, Stripe for web top-up.

**No accounts were created and no keys exist.** `.env.example` lists every
variable name with no values. You create the projects and paste the keys.

## What is verified, and what is not

Run it yourself:

```bash
npm run test:db           # migrations + RLS + ledger, needs local Postgres 15+
npm run test:quote        # the quote engine, 22 cases
npm run test:data         # the in-memory ledger, 15 cases
npm run check:quote-sync  # client and server quote engines have not drifted
DENO=$(which deno) npm run test:functions
```

| layer | how it was checked | result |
| --- | --- | --- |
| 7 migrations | applied to a throwaway Postgres 16 | **all apply clean** |
| RLS isolation | two real users, acting as each in turn | **0 cross-user rows visible**, 9 privilege checks pass |
| Ledger behaviour | 8 scenario tests | **8 pass** |
| Ledger integrity | `reconcile_ledger()` after every test | **0 drift rows** |
| App typecheck | `npx tsc --noEmit` | **0 errors** |
| Quote engine parity | `scripts/sync-quote.sh --check` | **client and server in sync** |
| Edge Functions (15 files) | `deno check` + `deno lint` | **15 files, 0 errors, 0 lint problems** |
| Webhook signature verification | 7 Deno tests | **7 pass** (tamper, wrong secret, 5-min replay, swapped timestamp, malformed header, length-mismatch compare) |
| **Client/server quote parity, at runtime** | hashes+prices generated by the app under Node, asserted by the server under Deno | **3 pass, 7 cases** |
| **Edge Functions end to end** | **never served against a live stack** | **see below** |

### What is still unverified

The functions type-check, lint and pass their unit tests, but they have
**never been served against a live stack** — `supabase start` needs ~10 Docker
images and only 2 pulled on this connection. So what is proven is the code's
types and its pure logic; what is not proven is the wiring: whether a real
request with a real JWT reaches the right handler, whether the PostgREST
column names match, whether the storage signed-URL round trip works.

Expect integration-shaped breakage there, not type-shaped.

Two of those wiring bugs were already found and fixed by the typecheck:
`row.assets` and `g.models` are typed by Supabase as **arrays** for an
embedded to-one relation. Casting them straight to an object compiled fine
under the app's looser settings but yields `undefined` at runtime — meaning
the provider would have received no image URL and every single generation
would have failed. Both now go through a `one<T>()` normaliser that handles
either shape.

First thing to do when you have the keys:

```bash
supabase start                      # pulls the images once
supabase db reset                   # applies all 7 migrations + seed
npm run test:functions              # typecheck, lint, unit tests
supabase functions serve
```

Then walk the core loop once with `EXPO_PUBLIC_USE_REAL_BACKEND=1`.

## Five bugs the tests caught

All three would have reached production.

1. **`credit_purchase` inserted 5 columns from a 4-column select.** Every
   purchase would have failed outright — the user is charged by Apple and
   gets no credits. Caught the first time the RLS fixture ran a purchase.
2. **`submit_generation` omitted `quote_id` from its insert values.** Same
   class of bug, same outcome: nobody could generate anything.
3. **`credit_balances` leaked every user's balance to every user.** A
   Postgres view runs with its *owner's* privileges by default, which
   bypasses RLS on the underlying table entirely. User A's test showed two
   balance rows where there should have been one. Fixed with
   `with (security_invoker = true)`, and the test now asserts the row count.

Number 3 is the one worth remembering: RLS on tables does nothing for data
read through a view unless the view opts in.

A fourth was caught by `reconcile_ledger()` — the signup grant created credits
with no matching audit entry, so `remaining` and the entry sum drifted from the
very first user. Rather than fix that one call site, grants now write their
opening entry from an `after insert` trigger, so no future code path can
forget.

The fifth is the embedded-relation cast described above, caught by
`deno check` — the one that would have broken every generation.

## Auth

- **Apple, Google, email OTP** via Supabase Auth. Sign in with Apple is
  mandatory on iOS once any other social login is offered.
- A `users` row and the 30-credit welcome grant are created by an
  `on auth.users insert` trigger, not by the client — the client cannot
  grant itself credits.
- **Account deletion that actually deletes** (`POST /account/delete`), run by
  the `deletions` job: storage objects removed from both buckets, then
  `auth.admin.deleteUser`, which cascades every table. Apple requires this
  for any app with sign up.
- **Consent gate (F38).** `submit_generation` raises `consent_required` unless
  `users.consent_at` is set. Enforced in the database, so no route can skip it.

## Database

- 7 migrations in `supabase/migrations/`, applied by `supabase db reset`.
- RLS on **all 16 tables**. Clients read their own rows; the ledger is
  read-only to them and has no write policy at all.
- Privileges are **stated explicitly** rather than inherited from Supabase's
  defaults (`revoke all on all tables ... from anon, authenticated`, then
  grant back only what is intended). A stray default grant cannot open a hole.
- Every security-definer function is revoked from `anon` and `authenticated`,
  so a user token cannot call `spend_credits` or `credit_purchase` even by
  name. Tested.
- Backups: **you must switch these on.** Supabase runs daily backups on Pro;
  the free tier does not. Do it before real users exist.

## Payments

- **In-app:** RevenueCat over Apple IAP and Google Play Billing. One webhook
  for both stores.
- **Web:** Stripe Checkout. Never a card form of our own.
- **No subscriptions at all**, so there is nothing to cancel — which was the
  single largest complaint in `fixes.md` (39 of 107 reviews).
- Webhook safety, all three layers:
  1. signature verified before the body is read (Stripe HMAC with a 5-minute
     replay window; RevenueCat bearer token) using a constant-time compare
  2. the provider's event id is inserted into `webhook_events`; a duplicate
     insert returns `{replay: true}` and stops
  3. `credit_purchase()` is keyed on the provider's transaction id and
     returns 0 on a replay
  Stripe and RevenueCat both retry. Any one of those three layers alone would
  eventually hand out free credits.
- `REFUND` and `CANCELLATION` mark the purchase refunded and never grant.
- `purchases.net_cents` records what actually lands after the store's cut —
  the number that decides whether this is a business.

## Jobs

`pg_cron` calls the `jobs` function with `JOBS_SECRET`; not reachable with a
user token.

| job | schedule | does |
| --- | --- | --- |
| `poll` | 20 s | advance live jobs; on success copy the output into our own bucket (the provider's URL expires) and push; on failure refund and push |
| `reap` | 5 min | anything running >15 min → failed + refunded |
| `expire` | hourly | write `expire` entries for lapsed grants |
| `purge` | hourly | delete source photos past `purge_after` (F39) |
| `deletions` | hourly | fulfil deletion requests |
| `sweep` | daily | drop old rate-limit windows |
| `reconcile` | nightly | assert the ledger balances; log drift |

## Security checklist

- [x] secrets only in env vars; `.env*` gitignored; only `EXPO_PUBLIC_*` reaches the bundle
- [x] input validated on the server on every route (`_shared/validate.ts`), including a cap on params size
- [x] authorisation checked on every read and write, **tested with a second user**
- [x] user id taken from the verified JWT, never from the request body
- [x] rate limits on the expensive routes (quote 120/min, submit 30/min, upload 60/hr, check-in 10/hr); Supabase rate limits auth itself
- [x] webhooks verify signatures, constant-time, with a replay window
- [x] uploads: size and MIME limits enforced server-side before the signed URL is issued; private buckets; signed URLs only
- [x] storage paths namespaced by user id, enforced by a storage policy
- [x] no user data in URLs; ids only in paths
- [x] model cost data (`unit_cost_cents`) stripped from the catalogue response
- [x] source photos auto-purged 24h after upload
- [x] `npm audit` run: **33 advisories (22 high, 11 moderate), all transitive
      through `@expo/cli` and `react-native`'s build toolchain** — `braces`,
      `node-forge`, `postcss-selector-parser`, `uuid`. These are bundler and
      CLI dependencies, not code that ships in the Hermes bundle.
      `npm audit fix --force` would downgrade Expo and break the build, so
      the fix is an Expo SDK upgrade when one lands, not a forced resolution.
      Re-check at deploy; nothing here is reachable by a request to the app.
- [ ] **privacy policy not written** — must list Supabase, fal.ai, RevenueCat, Stripe, Expo. Blocks store submission.
- [ ] **database backups not enabled** — needs a Supabase plan
- [x] Edge Functions type-check and lint clean (15 files), webhook signature
      verification tested (7 cases), client/server quote parity tested across
      Node and Deno
- [ ] **Edge Functions never served against a live stack** — integration
      wiring is the remaining unknown
